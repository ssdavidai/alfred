# Wasp / Prisma migrations

The web container runs `prisma migrate deploy` against the migrations in this
directory on boot. This dir is Wasp-managed: `wasp build` copies it into
`.wasp/build/db/migrations/`, which becomes the server image's migration set.

## Why a STABLE baseline matters (finding B4)

Today only `migration_lock.toml` is committed here, so CI (`build-web.yml`)
**regenerates** the `0_init` baseline from the Wasp-expanded schema on every
build via `prisma migrate diff --from-empty`.

That is safe for a fresh DB, but **latent-dangerous for an existing tenant**:
`_prisma_migrations` records the checksum of the `0_init` that was applied.
If a future `schema.prisma` change (or a Wasp/Prisma version bump) makes the
regenerated baseline's SQL differ, its checksum no longer matches the recorded
one and `prisma migrate deploy` **aborts** — the web container never starts.

`build-web.yml` now prefers a **committed** `0_init/migration.sql` and only
regenerates when none is committed. Committing a stable baseline freezes the
checksum and removes the regeneration hazard.

## How to commit the stable baseline (human, one-time)

The baseline must be generated from the **Wasp-expanded** schema (Wasp injects
the auth entities — Auth / AuthIdentity / Session — that are not in the
source `schema.prisma`), so it must be produced in a real Wasp environment,
NOT hand-written:

```bash
cd packages/web
wasp build                       # writes .wasp/build/db/schema.prisma (expanded)

mkdir -p migrations/0_init
npx -y prisma@5.19.1 migrate diff \
  --from-empty \
  --to-schema-datamodel .wasp/build/db/schema.prisma \
  --script > migrations/0_init/migration.sql

git add migrations/0_init/migration.sql migrations/migration_lock.toml
```

### IMPORTANT — protecting tenants that are ALREADY deployed

A freshly generated baseline may not byte-match the `0_init` that an existing
tenant already applied (if it was generated by an older CI build). For each
such tenant, after deploying the image that carries the committed baseline,
run **once** inside the web container so Prisma records the baseline as already
applied instead of trying to re-run / re-checksum it:

```bash
npx prisma migrate resolve --applied 0_init
```

Fresh tenants need nothing — `prisma migrate deploy` applies `0_init` normally.
